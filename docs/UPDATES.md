# Publishing official ClawPal releases

The only official repository is **https://github.com/Kaayoos/clawpal**.
The app uses `https://api.github.com/repos/Kaayoos/clawpal/releases/latest`.
It rejects drafts, prereleases, other repositories, mismatched tags/versions,
wrong boards/layouts, incorrect image sizes/chips and SHA-256 mismatches.
Automatic checks run on launch and every six hours and can be disabled.

## Assets and format

Every stable release has a `vX.Y.Z` tag and these assets:

- `ClawPal-Setup.exe`, its `.sha256`, and `ClawPal-licenses.zip`.
- `clawpal-release.json` (schema 2, generated by scripts/package-release.ps1).
- One `clawpal-*.bin` application image for every entry in `boards/catalog.json`,
  including both 7-inch flash sizes. These are never merged flash images.
- `ClawPal-source.zip`, matching esptool and PresentMon source archives, and the
  recursive ESP-IDF source archive with submodules and its build instructions.

The schema-2 envelope contains `schema`, `version`, and `boards`. Each entry
in `boards` contains a schema-1 firmware record: `schema`, `version`, `board`,
`layout`, `min_companion`, and `firmware` with `file`, `bytes`, `sha256`. The
companion chooses exactly its paired board ID. Every record must have the same
version as the envelope and `vX.Y.Z` tag. A missing model is never replaced with
a similarly sized one. The original 16 MB layout `ota-v1` has a 0x3f0000-byte
minimum OTA slot; `ota-8m-v1` has two 0x300000-byte slots. Firmware itself checks
its board ID, layout and size before writing. Older single-board manifests are
still understood by the new companion. Update the PC companion to 0.8.0 first.
An incompatible companion is offered as a PC update, while firmware installation
stays disabled until the companion meets `min_companion`.

Firmware that asks for on-screen approval (`POST /confirm`) refuses Wi-Fi and
firmware changes from companions that do not ask for it. The first release
containing it must raise `min_companion` in `scripts/package-release.ps1` (and
the bundled value in `FirmwareUpdates.Install`) to that same release's version,
so that companions update before their display does.

## First publication: commands for the maintainer

Create an empty **Kaayoos/clawpal** repository on GitHub first if it does not
already exist. Do not initialize a second README or license there. Authenticate
Git for your own GitHub account. Run these in PowerShell from your ClawPal folder:

```powershell
# Run inside the ClawPal repository; these commands publish it.
git config user.name "MinimalPulse"
git config user.email (Read-Host "Your verified GitHub email or GitHub noreply address")
python scripts/check-publication.py
if ($LASTEXITCODE -ne 0) { throw "Resolve publication findings first" }
git add .
git diff --cached --stat
git commit -m "Release ClawPal 0.8.1"
if ($LASTEXITCODE -ne 0) { throw "Commit failed" }
git branch -M main
$remote = git remote get-url origin 2>$null
if ($LASTEXITCODE -ne 0) { git remote add origin https://github.com/Kaayoos/clawpal.git }
elseif ($remote -ne "https://github.com/Kaayoos/clawpal.git" -and $remote -ne "git@github.com:Kaayoos/clawpal.git") { throw "Review the existing origin before publishing" }
git push -u origin main
if ($LASTEXITCODE -ne 0) { throw "Push failed; do not force push" }
git tag -a v0.8.1 -m "ClawPal 0.8.1"
if ($LASTEXITCODE -ne 0) { throw "Tag already exists or could not be created" }
git push origin v0.8.1
```

Review the staged diff before the commit if you have made additional changes.
Use your own verified/noreply email, not a tool's identity. No tool is an author
or coauthor. GitHub contributor attribution follows actual commit metadata;
curated release notes do not generate a contributor list.

## What the tag does

The release workflow runs only for Kaayoos/clawpal. It calls the same tested
build workflow: builds firmware with ESP-IDF 5.5.2, packages Windows, verifies
the matching tag, collects licenses, and creates corresponding source archives.
It first uploads all assets into a draft release, then publishes it as the latest
stable release. This prevents the updater from seeing a half-uploaded release.
The release body comes from `docs/releases/X.Y.Z.md`, never auto-generated notes.
If publication fails, inspect the Actions logs and any draft before retrying;
do not replace an already-published version with different bytes.

For subsequent versions, update firmware/CMakeLists.txt and the companion's
Version, update the versioned user agent/log strings, add curated release notes,
build/test locally and commit. Push the matching new `vX.Y.Z` tag. Keep SDK/runtime
versions and notices aligned when changing dependencies. Adjust min_companion
only when protocol changes require it. Include corresponding source and retained
third-party licenses with every binary redistribution, including mirrors.

## User update behavior

Checks only propose updates. Download the PC installer from Updates, exit the
running companion using its tray menu, and run the newer installer. It upgrades
the per-user executable and retains configuration. Equal/older installers do not
silently replace newer installations. Then choose the display update in Updates.
Wi-Fi OTA writes only the inactive application slot, preserves settings, and
waits for the new version's boot confirmation. Keep power connected. A future
partition/bootloader migration can require a separate USB operation.

The GitHub Actions workflow cannot be exercised before the source is pushed.
The real official update feed cannot return an update until a release is public.
Local contract tests validate the same metadata and manifest structure offline.
